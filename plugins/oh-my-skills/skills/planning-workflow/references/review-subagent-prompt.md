# 独立计划评审提示词

用于 `planning-workflow` 第 6 节的 C5 通道：通过外部评审命令（如 Claude 上的 `$codex:rescue`）或无上下文的子 agent，对一份计划做只读评审。

本文件是评审任务和输出格式的唯一来源。调用方只负责提供计划路径、需求摘要路径和只读边界。

## 输入

- 计划文件：调用方给出
- 需求与上下文摘要：调用方给出；缺失时自行从计划和仓库推断，并在报告里标注"上下文缺失"
- 仓库：当前工作目录
- 项目规则：`CLAUDE.md`、`AGENTS.md`、`README.md` 等（如存在）

## 只读边界

可以读取文件、查看现有 diff 与 status。**不得修改、删除或创建文件，不得安装依赖、提交或发布，不得执行验收命令。** 读不到的信息写"未读取"，不要猜测，不要发送空消息。

## 任务清单

1. **需求覆盖**：计划里每个 Phase 是否都能追溯到一条明确需求？有没有需求没有任何 Phase 承接？
2. **验收标准可执行性**：逐条检查 Acceptance Criteria 是不是可直接运行的命令。出现"验证是否正常""确认无误""检查是否生效"这类措辞即标记为缺陷。
3. **约束可核查性**：每条 Constraint 是否有对应的命令能在验收阶段证明它成立（行数、测试数、文件数等）。
4. **量化声明落地**：Design 段落里出现的数字（行数、维度、模型名、超时值）是否都有匹配的 Constraint。
5. **跨阶段一致性**：Phase N 引用的类型、函数签名、文件路径是否与 Phase N-1 的产出对得上。
6. **范围蔓延**：是否包含需求之外的工作；Scope 的 Out 段是否与正文自相矛盾。
7. **风险与回滚**：破坏性操作、数据迁移、配置变更是否有失败回退路径。
8. **占位符残留**：`TBD`、`TODO`、"同上"、"类似 X"。
9. **假设的诚实性**：Phase 0 跳过澄清时，未经确认的判断是否被明确标为假设，而不是伪装成已确认结论。

## 严重度

| 级别 | 含义 |
|---|---|
| BLOCKER | 计划按现状执行会导致返工或错误交付，必须改完才能批准 |
| MAJOR | 会造成阶段卡顿或多轮返工，建议批准前修 |
| MINOR | 表达或结构问题，不影响执行 |
| NIT | 措辞建议 |

只报告有把握的问题。不确定的写"待确认"，不要凑数。不要为了显得全面而列出计划里本来就正确的部分。

## 输出格式

```markdown
## 评审结论
BLOCKER: <n> / MAJOR: <n> / MINOR: <n> / NIT: <n>
建议：<批准 | 修改后批准 | 不可批准>

## 问题清单
| # | 级别 | 位置 | 问题 | 建议改法 |
|---|------|------|------|----------|
| 1 | BLOCKER | Phase 2 / Acceptance Criteria | `verify it works` 不是可执行命令 | 改为 `pytest tests/test_x.py -v` |

## 未覆盖的检查
- <读不到或无法判断的项，说明原因>
```

结论必须来自实际读取的计划内容。不要复述计划、不要重写计划、不要实施修复。
